MLA — Multi-Head Latent Attention

GQA and MQA shrink the cache by sharing key/value heads across query heads — fewer distinct vectors, each one the same size as before. DeepSeek's Multi-Head Latent Attention does something different: it keeps every head's information, but compresses each token's keys and values down into one small shared latent vector before anything is cached, and reconstructs the full per-head versions from that latent at attention time.

A bottleneck instead of a merge

Standard multi-head attention computes and caches a separate K vector and V vector for every head. MLA replaces that with a learned down-projection: a token's hidden state is compressed into a single low-dimensional latent vector, c_KV, and that latent — not the per-head keys and values themselves — is the only thing written to the cache. At attention time, a learned up-projection reconstructs the full-size, per-head keys and values back out of that one latent. Nothing is shared or duplicated across heads the way GQA merges them; each head still gets its own reconstructed key and value, recovered from a bottleneck that every head's information had to pass through together.

One wrinkle: rotary position embeddings depend on absolute position and don't commute cleanly with a shared low-rank compression, so applying RoPE directly to the compressed latent breaks the relative-position math attention relies on. DeepSeek's actual implementation works around this by splitting keys into two parts — most of each key's dimensions come from the compressed, position-free latent, while a smaller "decoupled" slice carries rotary position information and is computed and cached separately, shared across heads rather than compressed per-head. You can see this split directly in DeepSeek-V2's released model config: a kv_lora_rank of 512 for the compressed latent, alongside a qk_rope_head_dim of 64 for the decoupled rotary part.

How much smaller, really

DeepSeek-V2's paper states MLA "reduces the KV cache by 93.3%" compared to DeepSeek 67B, and reports a 5.76x increase in maximum generation throughput as a consequence. That's an end-to-end comparison across two different models, not a clean same-shape ablation — and DeepSeek 67B is itself dense, but it isn't plain multi-head attention either: its own released config shows 64 query heads sharing 8 key/value heads, i.e. it already used GQA. So the 93.3% figure is MLA against an already GQA-compressed cache, not against the naive MHA baseline the wording might suggest — if anything that makes the number more notable, not less.

The released DeepSeek-V2 config backs up a similar order of magnitude directly: it sets kv_lora_rank (the latent size) to 512 and qk_rope_head_dim (the decoupled rotary part) to 64, for 576 cached elements per token. You can see the saving in the shapes themselves in DeepSeek-V3's official inference code: the actual cache buffer is sized just kv_lora_rank elements per token, while the up-projection weight that reconstructs the full-size keys and values back out of it, wkv_b, is shaped n_heads * (qk_nope_head_dim + v_head_dim) — which for DeepSeek-V2's 128 heads at 128 dimensions each works out to 32,768 elements per token, the size an equivalently-shaped ordinary multi-head cache would need. That's roughly 57x fewer cached elements per token by that arithmetic — a number derived here from DeepSeek's own published config and code, not a figure either paper states outright, so treat the exact multiple as approximate even though the underlying numbers are real.

Where this shines, and where it doesn't

The headline result both DeepSeek papers report is that MLA gets a larger cache reduction than GQA typically achieves while matching or exceeding ordinary multi-head attention's quality — a combination GQA and MQA don't claim, since both trade away some quality for their memory savings. That's plausible precisely because MLA isn't sharing or discarding anything the way GQA does; it's a genuine dimensionality reduction with a decompression step built into the architecture, so a well-trained down/up-projection pair can in principle preserve more of what each head needs than forcing multiple heads to agree on one shared key ever could. The cost is complexity: MLA needs the down-projection, the up-projection, the decoupled-RoPE workaround, and (for the up-projection to not become a speed bottleneck at inference) a matrix-absorption trick that folds it into neighboring projections rather than ever materializing full per-head keys explicitly. And like GQA/MQA, it's a pretraining-time architecture decision — you cannot retrofit MLA onto an existing ordinary-attention checkpoint the way any press in the catalogue can run against any model as-is, and so far it's been proven out primarily inside DeepSeek's own model family rather than independently replicated as widely as GQA has been.

Real implementation

Original papers: DeepSeek-AI, "DeepSeek-V2: A Strong, Economical, and Efficient Mixture-of-Experts Language Model," 2024, which introduces MLA, and DeepSeek-AI, "DeepSeek-V3 Technical Report," 2024, which carries MLA forward largely unchanged. The kv_lora_rank, q_lora_rank, qk_rope_head_dim, qk_nope_head_dim, and v_head_dim values cited above are read directly from DeepSeek-V2's released config.json. The MLA module itself, including the projection and cache logic, is in DeepSeek-V3's official inference code: inference/model.py.
