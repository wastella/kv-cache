PagedAttention

Every method in the catalogue decides which KV entries to keep. PagedAttention doesn't touch that decision — it changes where the entries you've already decided to keep live in GPU memory. Not compression itself, it's what determines whether a compression technique's savings actually turn into more sequences served, or vanish into fragmentation.

Reserving for the worst case

A naive serving system has to put each sequence's KV cache somewhere, and the simplest place is one contiguous slab of GPU memory per sequence — contiguous because the attention kernel expects to walk a sequence's keys and values as a single block. The problem is that a slab has to be sized before you know how long generation will actually run, so it gets sized for the worst case: the model's maximum context length. A request that generates 40 tokens still reserves room for, say, 4096 — the other 4056 slots sit there empty for the lifetime of the request, unusable by any other sequence even though nothing is stored in them.

Kwon et al. measured this waste directly in existing serving systems and found 60–80% of allocated KV cache memory going unused — internal fragmentation from sizing every request for a length it will almost never reach, plus external fragmentation as slabs of different reserved sizes leave unusable gaps between each other. Worse, because each sequence's cache is a separate contiguous slab, there's no way to let two sequences share memory even when they'd benefit from it — a shared system prompt prefix, or the parallel branches of a beam search, each get their own full copy.

Pages, not one contiguous block

PagedAttention borrows the fix straight from operating-system virtual memory. Instead of one contiguous slab, a sequence's KV cache is split into fixed-size blocks (kvpress and the catalogue call the unit a "token"; vLLM calls it a "block" or "page" — same idea, a fixed chunk of storage), each holding the key and value vectors for a fixed number of positions. A per-sequence block table maps logical positions — "this sequence's 5th block" — to wherever that block actually lives in physical GPU memory, which does not need to be next to the sequence's other blocks at all. The attention kernel is rewritten to read through this indirection instead of assuming a flat contiguous span.

New blocks are allocated one at a time, only when a sequence actually generates enough tokens to fill the current one, and freed back to a shared pool the instant the sequence finishes. Nothing is ever reserved ahead of need. vLLM reports this brings fragmentation from that 60–80% figure down to under 4%. The same indirection also makes sharing nearly free: two sequences with an identical prompt prefix can point the same logical blocks at the same physical blocks, and only fork a private copy — copy-on-write, with reference counting — the moment one of them actually writes something different. vLLM's authors report this cuts memory overhead by up to 55% for memory-heavy sampling patterns like beam search.

Try it

Two toy sequences, A and B, share a GPU with room for 40 physical blocks of 16 tokens each (640 tokens total). The model's maximum context length is 512 tokens — 32 blocks. Drag each sequence's length and watch what each allocation strategy actually reserves.

Illustrative, not measured. The block size (16), pool size (40 blocks), and max length (512) are round numbers chosen to make the contrast legible, not values pulled from a real deployment. The shape of the difference — reserve the max vs. allocate on demand — is the real mechanism from the paper.

What this buys you, and what it doesn't

PagedAttention doesn't reduce how much KV data logically exists for a given sequence and compression ratio — that number is set entirely by whatever's upstream of it: the model's architecture (see GQA/MQA, MLA) and whichever catalogue press, if any, is evicting entries. What it eliminates is the gap between that logical size and the physical memory a naive system would have burned reserving room for it. That's exactly why it composes with everything else on this site rather than competing with it: run StreamingLLM or H2O on top of a paged KV cache and you shrink the logical cache further, on top of memory that was already being allocated efficiently. The two savings stack.

The cost is indirection. Every attention computation now walks a block table instead of reading a flat array, which is real kernel complexity vLLM had to solve with custom CUDA — and picking a good block size is its own tradeoff: too small and the per-block bookkeeping overhead and kernel launch cost start to matter; too large and you're back to wasting the tail end of the last block per sequence (bounded internal fragmentation, but never zero). None of this is visible to a user of the system — it's the reason vLLM reports 2–4× the throughput of prior serving systems at the same latency, serving more concurrent sequences on the same GPU than a naive implementation, without changing a single output token.

Real implementation

vLLM is the reference implementation and the system the original paper was built around. Its kernel design doc walks through block size, physical block numbers, and the block-offset arithmetic the attention kernel actually uses — vLLM itself now flags this doc as historical, describing the original kernel rather than the current code, but the block-table mechanics it explains are still the right mental model: docs.vllm.ai — PagedAttention kernel design. The block allocator itself now lives in vLLM's V1 engine, in KVCacheManager: vllm/v1/core/kv_cache_manager.py. Source: vllm-project/vllm on GitHub.
