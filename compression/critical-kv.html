CriticalKV

TL;DR: Every scoring method in this catalogue asks some version of "how much attention does this token get?" CriticalKV asks a different question on top of that: once a token's value vector actually gets projected into the model's output, how much does it move that output? It doesn't replace your scoring method, it rescales it.

Attention isn't the same as impact

Feng, Lv, Guo, Cao, Zhou, and Xie's paper frames KV cache eviction as an output perturbation problem: the thing that actually matters isn't how much attention weight a cached token earns, it's how much the model's final output changes if you evict it. Those two things usually track each other, but not always. A token's value vector still has to pass through the attention head's output projection (W_o) before it affects anything downstream, and a token that gets moderate attention but whose value lands in a direction W_o amplifies can matter more than a heavily-attended token whose value gets projected into something closer to a null direction.

CriticalKV doesn't compute this from scratch. It wraps an existing ScorerPress (SnapKV, Knorm, whatever you'd otherwise use) and rescales that press's scores using ‖(V · W_o)‖₁: the L1 norm of each token's value vector after being passed through the output projection, averaged across query groups when the model uses grouped-query attention. Higher projected norm means this token's value pushes the output further, so its score gets amplified; a token the base press already liked but whose value barely moves the output gets pulled back down.

Two stages, so the rescale can't backfire

Rescaling by an unrelated signal is risky on its own: if the base press's top pick happens to have a small projected-value norm, a naive rescale could bump it out of the kept set entirely, discarding a token the underlying method was confident about. CriticalKV guards against that with a two-stage split, controlled by first_stage_ratio (default 0.5):

Stage 1 takes the base press's own scores and locks in the top first_stage_ratio fraction of the eventual budget, untouched by anything that follows. Stage 2 then rescales every token's score by the projected value norm, and writes the stage-1 survivors back in at the maximum representable score, so the rescale can shuffle the rest of the ranking but can never displace what stage 1 already guaranteed. The final kept set still comes from a standard top-k over these combined scores, the same int(k_len * (1 - compression_ratio)) budget every ScorerPress on this site uses.

CriticalAdaKV: the same rescale, with adaptive per-head budgets

kvpress also ships CriticalAdaKVPress, which combines this rescaling with AdaKV-style adaptive head-wise compression: each attention head gets its own kept-token budget (proportional to how much of the total top-scoring mass falls in that head, subject to an alpha_safeguard minimum per head) instead of every head getting the same flat share. Within each head's budget, the same stage-1/stage-2 CriticalKV rescale decides which tokens fill it. Mechanically it also works differently from most presses on this site: rather than trimming the K/V tensors it returns, it computes which (batch, head, position) triples to mask out and stores them on the module for the attention computation to apply directly.

Where this shines, and where it doesn't

Because it's a wrapper, CriticalKV is a way to squeeze more accuracy out of a scoring method you're already using, not a competing alternative to it. The paper reports that layering it on top of three existing eviction methods roughly halves their average compression loss across a 29-dataset evaluation spanning the Ruler and LongBench benchmarks. The cost is real, though: computing V · W_o per head is extra work on top of whatever the wrapped press already costs, and it needs direct access to the model's output-projection weight matrix and its grouped-query head layout, which ties the current implementation to models kvpress can introspect that way. It's also easy to double-count: the source explicitly warns against wrapping ExpectedAttentionPress with use_vnorm left enabled, since that press already does a similar value-magnitude rescale on its own.

Real implementation

kvpress implements this as CriticalKVPress (wraps any ScorerPress) and CriticalAdaKVPress (the AdaKV-combined variant). See the source: criticalkv_press.py. Original paper: Feng, Lv, Guo, Cao, Zhou, Xie, "CriticalKV: Optimizing KV Cache Eviction from an Output Perturbation Perspective," 2025.
