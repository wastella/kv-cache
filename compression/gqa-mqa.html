compression / architecture-level

GQA / MQA

Every page in the catalogue changes what an already-trained model does — evicting tokens, quantizing numbers, shrinking per-layer budgets — without touching a single weight. Grouped-Query and Multi-Query Attention are decided before any of that: they change how many key/value heads the model has, so the cache starts out smaller at the very first token, before any press gets a chance to compress anything.

Multi-head attention's hidden cost

In ordinary multi-head attention, every query head gets its own key head and its own value head. A layer with 32 query heads computes and caches 32 separate K vectors and 32 separate V vectors per token — the cache grows linearly with num_heads, on top of growing linearly with sequence length. Nothing about the attention mechanism requires that one-to-one pairing between query heads and key/value heads; it's just the default architecture choice, and it's the one lever GQA and MQA reach for.

Two ways to break the pairing

Shazeer's observation: autoregressive decoding is usually bottlenecked by memory bandwidth, not compute. Every decoding step has to reload the entire key/value cache, and that cost scales with how many distinct K/V vectors exist per token, not with how much arithmetic the model does. Multi-Query Attention (MQA) is the blunt fix: collapse every query head down to a single shared K vector and a single shared V vector. Cache size drops by a factor of num_heads — 32 heads means a 32x smaller cache — at the cost of some quality, which the paper reports as "much faster [decoding]... with only minor quality degradation."

MQA's cut is extreme enough that it starts to hurt more as models get larger. Ainslie et al. proposed the interpolation: Grouped-Query Attention (GQA) splits query heads into G groups and lets every head within a group share one K/V head. G = 1 recovers MQA exactly; G = num_heads recovers ordinary multi-head attention; anything in between is a tunable knob on the memory/quality tradeoff. Their paper also gave existing checkpoints a way in without retraining from scratch: "uptrain" an already-pretrained multi-head model into a grouped-query one using roughly 5% of its original pretraining compute, converting by averaging each group's existing key/value heads together into one. The result they report: "quality close to multi-head attention with comparable speed to multi-query attention."

Try it

8 illustrative query heads, grouped down to however many key/value heads the slider allows. Drag it to 1 and every query head shares one K/V head — MQA. Drag it to 8 and every query head gets its own — full MHA. At 1 shared head, this demo's 8:1 ratio matches Llama 2 and Llama 3's 70B models exactly: 64 query heads, 8 key/value heads.

A knob you can't turn at inference time

A press like SnapKV or StreamingLLM runs against whatever cache a model produces, on any model, at request time — you can turn the compression ratio up or down per call. GQA and MQA don't work that way: the number of key/value heads is baked into the model's weights, chosen (or converted into, via uptraining) before it's ever served. You cannot point a GQA-style press at a plain MHA checkpoint and get this saving for free; the model has to have been built, or converted, with fewer K/V heads in the first place. What the catalogue's presses can do is stack on top of it — a press evicting half the cache of a GQA model is still evicting half of a cache that started out several times smaller than an MHA model's would have.

Where this shines, and where it doesn't

GQA in particular has become close to a default choice for production-serving-oriented open models, because the tradeoff is unusually favorable: near-MHA quality, a cache smaller by whatever factor the group count buys, and faster decoding as a direct consequence of moving less memory per step. MQA's more extreme cut still shows up where memory bandwidth matters more than the last bit of quality. The real limitation is inflexibility: the group count is a single number chosen once for the whole model, not something that can be dialed differently per request, per layer's actual need (that's closer to what PyramidKV does, on the catalogue side), or adjusted after the fact if it turns out to be too aggressive for some downstream task.

Real implementation

Original papers: Shazeer, "Fast Transformer Decoding: One Write-Head is All You Need," 2019 (MQA) and Ainslie, Lee-Thorp, de Jong, Zemlyanskiy, Lebrón, Sanghai, "GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints," 2023. This is production technology, not a research curiosity — you can read the head counts directly out of released model configs: Llama 2 70B and Llama 3 70B both use 64 query heads with 8 key/value heads (num_attention_heads: 64, num_key_value_heads: 8), and Mistral 7B uses 32 query heads with 8 key/value heads.
