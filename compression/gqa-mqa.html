compression / architecture

GQA / MQA

TL;DR: Share key/value heads across query heads instead of giving every query head its own. Fewer distinct K/V vectors per token means the cache gets smaller. Multi-Query Attention takes the sharing all the way down to one head and Grouped-Query Attention stops partway, at a handful of groups.

Multi-head attention

In ordinary multi-head attention, every query head gets its own key head and its own value head. A layer with 32 query heads computes and caches 32 separate K vectors and 32 separate V vectors per token, meaning the cache grows linearly with num_heads, on top of growing linearly with sequence length. GQA and MQA challenge that architectural choice to compress the cache.

Two ways to break the pairing

The key observation is that the decoding stage is usually bottlenecked by memory bandwidth, not compute. Every step has to reload the entire key/value cache, which is the main cost when generating tokens. Multi-Query Attention (MQA) fixes this by collapsing every query head down to a single shared K vector and a single shared V vector. Cache size drops by a factor of num_heads (32 heads means a 32x smaller cache) at the cost of some quality, which the paper reports as "much faster [decoding]... with only minor quality degradation."

MQA's cut is extreme enough that it starts to hurt more as models get larger. Grouped-Query Attention (GQA) is a gentler option. It splits query heads into G groups and lets every head within a group share one K/V head. G = 1 recovers MQA exactly; G = num_heads recovers ordinary multi-head attention; anything in between is a tunable knob on the memory/quality tradeoff. By doing this, they achieve "quality close to multi-head attention with comparable speed to multi-query attention."

Try it

A knob you can't turn at inference time

An inference-time compression method runs against whatever cache a model produces, on any model, at request time: you can turn the compression ratio up or down per call. GQA and MQA don't work that way: the number of key/value heads is baked into the model's weights, chosen (or converted into, via uptraining) before it's ever served. You cannot point an inference-time method at a plain MHA checkpoint and get this saving for free; the model has to have been built, or converted, with fewer K/V heads in the first place. What inference-time compression can do is stack on top of it: a method evicting half the cache of a GQA model is still evicting half of a cache that started out several times smaller than an MHA model's would have.

Where this shines, and where it doesn't

GQA in particular has become close to a default choice for production-serving-oriented open models, because the tradeoff is unusually favorable: near-MHA quality, a cache smaller by whatever factor the group count buys, and faster decoding as a direct consequence of moving less memory per step. MQA's more extreme cut still shows up where memory bandwidth matters more than the last bit of quality. The real limitation is inflexibility: the group count is a single number chosen once for the whole model, not something that can be dialed differently per request, per layer's actual need, or adjusted after the fact if it turns out to be too aggressive for some downstream task. MLA is the other architecture-time answer to the same cache-size problem, via a different mechanism (a shared low-rank bottleneck instead of head sharing). And whatever the cache ends up shrunk to here, a serving system still has to place it in GPU memory efficiently, which is PagedAttention's job, not this page's.

Real implementation

Original papers: Shazeer, "Fast Transformer Decoding: One Write-Head is All You Need," 2019 (MQA) and Ainslie, Lee-Thorp, de Jong, Zemlyanskiy, Lebrón, Sanghai, "GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints," 2023. This is production technology, not a research curiosity: you can read the head counts directly out of released model configs: Llama 2 70B and Llama 3 70B both use 64 query heads with 8 key/value heads (num_attention_heads: 64, num_key_value_heads: 8), and Mistral 7B uses 32 query heads with 8 key/value heads.
