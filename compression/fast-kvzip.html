KVzap & Fast KVzip

TL;DR: KVzip scores every cached KV pair by actually reconstructing the original context with the model itself, which is accurate but requires an extra forward pass. KVzap and Fast KVzip are two later methods, from two different labs, released close together, that both replace that reconstruction with a small trained model predicting the same kind of score directly. They're not two names for the same thing: they're two different architectures chasing the same shortcut.

What they're both approximating

KVzip (Kim et al., "Query-Agnostic KV Cache Compression with Context Reconstruction," arXiv 2505.23416) scores a cached KV pair by using the LLM itself to reconstruct the original context from the compressed cache, teacher-forced, and recording the maximum attention that pair receives during the reconstruction. Pairs the reconstruction barely needs get pruned. It's accurate specifically because it's not a proxy, it's the model telling you, via an actual forward pass, what it would have used, and reusable across future queries once computed. The catch is exactly that forward pass: reconstructing the context costs real compute on top of the original prefill, for every context you want to compress. The paper reports a 3-4x cache size reduction and roughly 2x faster decoding with FlashAttention, negligible accuracy loss.

KVzap and Fast KVzip both start from the same premise: whatever signal KVzip's reconstruction is measuring, can a small model just predict it directly from hidden states, skipping the reconstruction pass entirely? Both are literally trained (offline, on a target model) to imitate that signal. Neither is derived from or wraps the other, and neither wraps KVzip's own kvpress implementation, they're independent presses in their own right.

KVzap: one small regressor per layer

kvpress's KVzapPress (Jegou, Jeblick, "KVzap: Fast, Adaptive, and Faithful KV Cache Pruning," arXiv 2601.07891) is about as simple as a learned scorer gets. Its score() runs the current layer's hidden states through one small trained module, either a plain linear layer or a 2-layer MLP (model_type controls which), and returns whatever comes out as the importance score, no further logic. There's one such module per transformer layer, loaded from a real checkpoint on the Hub named after the target model, e.g. nvidia/KVzap-mlp-Qwen3-8B. It runs during both prefilling and decoding, unlike KVzip's own reconstruction, which only makes sense as a one-time prefill pass. The paper reports 2-4x compression with negligible accuracy loss and state-of-the-art results on the kvpress leaderboard at time of writing.

Fast KVzip: a trained per-head gate, plus hand-coded guardrails

kvpress's FastKVzipPress (Kim, Han, Yun, NAVER AI Lab, "Fast KVzip: Efficient and Accurate LLM Inference with Gated KV Eviction," arXiv 2601.17668) is architecturally more involved. Each layer gets its own trained FastKVzipGate: small query/key projections (down to a 16-dimensional space by default) with RMSNorm, a learned per-head "base" vector standing in for the sink positions, and a sigmoid-shaped score comparing each token's projected key against both the live query stream and that base. It's a genuinely different, more head-aware design than KVzap's flat regressor. Its checkpoints come from the original authors' release on the Hub, loaded through kvpress's load_fastkvzip(); the docstring points to the original repository for a fully optimized version with actual chunked-prefill compression, since kvpress's implementation, by its own docstring, makes "minimal changes" rather than reproducing every optimization. The paper reports up to 70% KV eviction while maintaining performance.

On top of the learned score, FastKVzipPress hard-codes two overrides that have nothing to do with training: it forces the score of the first n_sink tokens (4 by default) to a certain-keep value, and does the same for a trailing window sized either as a fixed window_size or as a fraction (window_ratio, 2% by default) of the context length for shorter contexts. So sink and recent tokens survive no matter what the trained gate says about them; only the middle is left to the model. KVzapPress has no equivalent, whatever it does with sink or recency has to be something the model itself learned, kvpress doesn't hard-code any of it. One more real difference worth knowing: in kvpress, FastKVzipPress only scores and compresses during prefill (its forward hook checks and returns early otherwise), so despite the gate architecture being able to run per-token, this implementation doesn't currently sparsify during decoding the way KVzapPress does.

Simulated, and not an approximation of anything real. Unlike this catalogue's other demos, the shading on non-overridden tokens here isn't standing in for a known formula computed with placeholder numbers, it's an arbitrary value with no relationship to what either trained model would actually predict. There is no public formula for KVzap's or Fast KVzip's learned scores to approximate: that's the entire point of training a model instead of hand-deriving one. Only the sink/window override logic shown here (Fast KVzip mode) is real, verifiable behavior straight from the source.

Where this shines, and where it doesn't

A trained scorer can in principle pick up on patterns nobody would think to hand-encode into a formula, and both report substantial wins: KVzap at 2-4x compression, Fast KVzip at up to 70% eviction, both cheap enough to run inline rather than as a separate reconstruction pass. That's the whole appeal over KVzip itself.

The costs are specific to being learned rather than derived. Both need a checkpoint trained for the exact base model in use: KVzapPress builds its checkpoint name directly from model.config.name_or_path, and FastKVzipPress raises an error pointing you to the release page if no matching gate exists. Neither works out of the box on an arbitrary or fine-tuned model the way a formula-based method like Knorm or TOVA does; you either need the exact model covered by a released checkpoint or you need to train your own. And precisely because they're learned, neither is auditable the way a formula is: you can't read what a trained gate keyed on by inspecting the code, only by inspecting the weights themselves, and this page hasn't done that and can't fake having done it.

Real implementation

kvpress implements these as separate presses, kvzap_press.py and fastkvzip_press.py. KVzap paper: Jegou, Jeblick, "KVzap: Fast, Adaptive, and Faithful KV Cache Pruning," 2026. Fast KVzip paper: Kim, Han, Yun, "Fast KVzip: Efficient and Accurate LLM Inference with Gated KV Eviction," 2026 (NAVER AI Lab; original repository: Janghyun1230/FastKVzip). Both build on KVzip: Kim et al., "KVzip: Query-Agnostic KV Cache Compression with Context Reconstruction," 2025, which doesn't have its own page in this catalogue yet.
