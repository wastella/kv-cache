compression / merging

MergingPress

TL;DR: Every eviction method in this catalogue makes the same choice once a token loses: delete it, its value is gone for good. MergingPress wraps any of those scoring methods and changes only what happens to the losers: instead of deleting an evicted token outright, it folds its value into whichever surviving token's key looks most like its own.

A wrapper, not its own scorer

MergingPress doesn't decide who gets evicted; it takes any ScorerPress already in this catalogue (SnapKV, Knorm, Expected Attention, anything with a .score()) and runs that press's own top-k logic completely unchanged to pick survivors: n_kept = int(k_len * (1 - compression_ratio)), the same truncating formula every other press here uses. The eviction decision is identical to running that scorer bare. The one thing MergingPress inserts is a single step between deciding who's evicted and physically dropping their rows: a merge.

For every evicted token, it finds whichever surviving token has the most cosine-similar key vector, reusing keys the model already computed, no extra forward pass. Two gates decide whether that merge actually happens. similarity_threshold requires the best match to clear a minimum cosine similarity before any merge proceeds (the default, 0.0, means every evicted token merges into something). merge_fraction then keeps only the top fraction of evicted tokens, ranked by that similarity; the rest are dropped exactly like ordinary eviction, no merge at all. kvpress's own docstring calls this out as genuinely task-dependent: merging everything (merge_fraction=1.0) wins on retrieval-style tasks, while merging only the most similar 75% wins on extraction.

The merge weight blends two things: how similar the two keys are, and how much of the evicted token's value "energy," its L2 norm, there is relative to the target's own value norm, so a token whose value vector is much larger than its target's pulls the blended result further toward itself. Multiple evicted tokens can land on the same survivor; their weighted contributions and the survivor's own original value all get summed and divided by 1 + total weight, a running weighted average, not an overwrite. Keys are never touched, only kept keys are gathered, unmodified: most models bake rotary position information into keys, and blending key vectors from different original positions would produce a key that doesn't correspond to any real position. Values don't carry positional information the same way, so blending them is comparatively safe.

Where this idea actually comes from

kvpress is upfront about the provenance here: the docstring flags MergingPress with "🤖 automated agent contribution" and describes it as "inspired by" two papers, not a reference implementation of either. Token Merging (Bolya et al., ICLR 2023) gradually combines similar tokens in a Vision Transformer to speed up inference, on image patch embeddings, not KV cache entries, and with no eviction at all: every token's information stays somewhere in the merged set. D2O (Wan et al., 2024) does target the KV cache and does merge, using a similarity threshold to "re-discriminate the importance of currently discarded tokens, determining whether they should be recalled and merged with similar tokens" back into the live cache, closer in spirit, but D2O's mechanism revives tokens after they've already been evicted, rather than merging at the moment of eviction the way MergingPress does. Treat MergingPress as kvpress's own synthesis of an idea both papers point toward, not a reproduction of either paper's method or reported numbers.

Each token gets a synthetic key "direction" and value "norm" deterministically from its text, and the underlying importance score standing in for the wrapped scorer's .score() is synthetic too. The merge mechanics, cosine-similarity target selection, the two gates, the norm-weighted blend, mirror kvpress's actual merge() logic; the second gate's cutoff is computed here as a rank over the already-thresholded candidates rather than kvpress's tensor-wide quantile call, which can shift exactly which tokens land right at the fraction boundary.

Where this shines, and where it doesn't

MergingPress recovers some of what plain top-k eviction throws away for free: keys are already computed, so cosine similarity and a weighted sum cost far less than another forward pass, and it composes with literally any scorer in this catalogue since it only changes what happens after the cut, not the cut itself. The tradeoff is that "does this help" is inherently task-dependent, by kvpress's own account merge_fraction pulls in opposite directions for retrieval versus extraction, so there's no single default that's obviously right for every workload. Keys stay unmodified, so merging values doesn't solve the separate problem of surviving tokens carrying position gaps where evicted neighbors used to be; whatever position-management strategy a pipeline already needs (see the StreamingLLM page's note on KeyRerotationPress) is still needed independently. And because this is an agent-contributed synthesis rather than a peer-reviewed paper's own method, there's no published benchmark number to point to the way there is for PyramidKV or GQA.

Real implementation

kvpress implements this as MergingPress, a wrapper taking any ScorerPress via its press argument. See the source: merging_press.py. Papers it's inspired by: Bolya, Fu, Dai, Zhang, Feichtenhofer, Hoffman, "Token Merging: Your ViT But Faster," ICLR 2023 and Wan, Wu, Zhang, Xin, Tao, Zhu, Wang, Luo, Xiong, Wang, Zhang, "D2O: Dynamic Discriminative Operations for Efficient Long-Context Inference of Large Language Models," 2024.
