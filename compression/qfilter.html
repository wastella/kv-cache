Q-Filter

TL;DR: Knorm scores a key by a formula someone wrote down: its own length. Q-Filter scores a key by a formula nobody wrote down: a vector learned offline, once per model, that gets dotted against every cached key at inference time. Same shape of rule, keep the highest scorers, but the scoring function itself came from training, not from a hand-picked heuristic.

A filter instead of a formula

Every other single-formula method in this catalogue commits to a specific, human-legible rule ahead of time: Knorm bets on vector length, StreamingLLM bets on position. Godey, Devoto, Zhao, Scardapane, Minervini, de la Clergerie, and Sagot bet on something else: let the model's own trained geometry supply the rule. For each layer and each key/value head, Q-Filter learns one filter vector, the same size as a single key vector, meant to stand in for the "typical" query direction that head tends to produce. At inference, no query is needed at all: each cached key is scored by its dot product against that head's learned filter, score = -(filter · key), and the lowest raw dot products (least aligned with the filter) end up with the highest scores and survive.

The filters are trained once, offline, per model architecture, and published to a Hugging Face collection; kvpress downloads the right one automatically based on the model's name. That's a very different operating model from every heuristic in this catalogue: there's no formula to audit in the source code, because the actual rule lives in a set of trained weights that ship separately from both the model and kvpress itself.

Simulated, not measured. There is no trained Q-filter running in this browser, and there couldn't be: the real filters are architecture-specific weights fetched from Hugging Face at model load time. This demo assigns each token a synthetic "filter response" deterministically from its text, purely to show the shape of the eviction rule (score = -(filter · key), keep the least-aligned keys) once a real trained filter is doing the scoring.

Where this shines, and where it doesn't

At inference, this costs about what Knorm costs: one dot product per cached key, no observation window, no held-out queries, no attention matrix. But because the filter was fit to that architecture's actual query geometry during training rather than picked as a plausible-sounding correlation, it has more information to work with than a formula like -‖k‖₂ ever could. The paper reports 99% needle-in-a-haystack accuracy at 32x compression, matching attention-based methods on retrieval while beating simpler heuristic scorers on generation perplexity. The dependency that buys is real, though: a filter is trained for one specific architecture, and kvpress's loader raises an error rather than degrading gracefully if it can't find one for the model you're running. Point Q-Filter at a fine-tune or a checkpoint the filter wasn't trained for and there's no fallback, unlike Knorm or TOVA, which work on any model with zero setup because their rule doesn't depend on anything learned. And because the filter is fixed once per (layer, head) rather than computed from the live prompt, it represents a typical query for that head in general, not the specific question a given request is actually asking, the way an observation-window method like SnapKV or FINCH can.

Real implementation

kvpress implements this as QFilterPress. Its score() is -(q_filter * keys).sum(dim=-1), where q_filter is loaded per model via QFilters.from_pretrained from the nthngdy/q-filters-* Hugging Face collection, keyed off the model's name. See the source: qfilter_press.py. Original paper: Godey, Devoto, Zhao, Scardapane, Minervini, de la Clergerie, Sagot, "Q-Filters: Leveraging QK Geometry for Efficient KV Cache Compression," 2025.
