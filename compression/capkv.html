CapKV

TL;DR: Most attention-based methods here ask "how much attention has this token actually received?" CapKV asks a subtly different question: if this token were removed, how much unique, query-relevant information would the remaining cache lose? It scores tokens with a ridge-regression leverage score over their value vectors, not a running attention tally.

Two ingredients: relevance, then leverage

CapKV's score has two parts that get multiplied together. The first is a query-relevance weight, w_i: how well does this token's key align with what a future query is likely to look like? Since future queries don't exist yet at scoring time, CapKV borrows a trick from kvpress's own ExpectedAttentionPress: project the sequence's hidden states into query-space before rotary position embeddings are applied, rotate that by an averaged rotation matrix built from the next n_future_positions (default 512) RoPE angles rather than any single real position, then mean-pool the result over the whole sequence into one anchor vector per head. w_i is exp(tau * cosine_similarity(key_i, anchor)), with a numerically-stable max-shift before the exponential.

The second ingredient is a leverage score. Treat each token's value vector v_i as a proxy for the direction it contributes to future outputs. Build a per-head "capacity matrix" A = I + Σ w_i v_i v_i^T: a ridge-regularized (the identity term is the regularizer) second-moment matrix of every token's value vector, weighted by its own relevance. Score token i by s_i = w_i * v_i^T A^{-1} v_i, which is exactly the diagonal of what's called the "hat matrix" in ridge regression: it measures how much token i's own value vector points somewhere the rest of the weighted cache doesn't already cover. A token whose value looks like everyone else's contributes little leverage even if it's individually relevant; a token that's both relevant and geometrically distinct from the pack scores highest.

This is solved once per KV head via a real matrix inversion (torch.linalg.solve), not computed per token in isolation, which is worth dwelling on: unlike a per-key norm or a per-token attention sum, a leverage score is a property of a token relative to the whole retained set. Evict a different set of tokens and every remaining token's leverage score changes, because the matrix A itself changes. The first n_sink tokens (4 by default) skip this computation entirely and are just forced to the top of the ranking, the same "always keep the earliest few tokens" idea StreamingLLM uses, here acting as a floor under a much more elaborate score rather than the whole rule.

Try it

Double-bordered tokens are the sink, ranked above every other score so it's the last thing cut when the ratio gets aggressive. Raising tau sharpens the relevance weighting, concentrating it onto whichever tokens best match the synthetic query anchor.

Simulated, not measured, and simplified on purpose. A real leverage score can't be faithfully decomposed per token in a browser demo, it's a joint property of every retained token's value vector at once, computed by inverting a matrix that changes whenever the retained set changes. This demo separates the two real ingredients instead: a synthetic query-relevance weight (tau-controlled, matching the real w_i formula) multiplied by a synthetic "value distinctiveness" stand-in, which shows the shape of the idea without claiming to reproduce the actual matrix math.

Where this shines, and where it doesn't

Leverage scoring directly targets a failure mode attention-tally methods can miss: redundancy. If ten cached tokens all carry nearly the same information, a method that sums up attention may rate all ten as important and keep all ten, while a leverage-aware score recognizes that after keeping the first one or two, the rest add little marginal information and should rank lower. The relevance weighting on top means it isn't just deduplicating blindly, it still favors tokens a future query is likely to actually want, and by inheriting Expected Attention's future-query anchor trick, it never needs a real query at scoring time. The cost is a full matrix inversion per head every time the cache gets scored, real compute overhead beyond what a dot product or a norm costs; this page doesn't have a benchmarked number for that overhead to cite, so treat it as a structural cost to be aware of rather than a measured one. And because leverage is a joint property of the whole candidate set rather than a fixed per-token number, a token's score depends on exactly which other tokens happen to be in the pool at scoring time, which makes CapKV's behavior less directly interpretable than "this token has a small norm" or "this token got little attention."

Real implementation

kvpress implements this as CapPress, a subclass of ScorerPress. See the source: cap_press.py. kvpress's docstring names the source paper as arXiv 2604.25975; checking that identifier independently turns up Yang, Tang, Zhen, Lv, "Rethinking KV Cache Eviction via a Unified Information-Theoretic Objective," 2026, which frames CapKV as one instance of a broader information-theoretic reformulation of KV eviction under linear-Gaussian attention assumptions. The algorithm description above is drawn from kvpress's own detailed docstring rather than the paper's full text, so treat the paper attribution as confirmed but any claims beyond what's quoted from kvpress's docstring as unverified.
