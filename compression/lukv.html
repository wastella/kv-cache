LU-KV

TL;DR: PyramidKV gives every layer a shrinking share of one global compression ratio, using a single hand-picked pyramid formula, the same shape for every model. LU-KV asks the same "how much budget does each layer need" question, but per attention head as well as per layer, and instead of a formula, the shape comes from a curve fit ahead of time on real data for one specific model.

Still a budget wrapper, not a scorer

Like PyramidKV, LU-KV doesn't decide which tokens survive within a budget: it wraps a ScorerPress (defaulting to kvpress's ExpectedAttentionPress) and lets that scorer's own .score() rank tokens as usual. Where PyramidKV is implemented as a subclass of SnapKVPress that overrides only the budget calculation, LU-KV is a genuine wrapper that can take any scorer as an argument, and it decides budgets at a finer grain: not one number per layer, but one number per (layer, KV head) pair.

A curve instead of a formula

The budget comes from a precomputed array shaped [99, num_layers, num_kv_heads]: one row per integer compression-ratio percentage from 1% to 99%. Given a target ratio, LU-KV looks up target_idx = round(ratio * 100) - 1 and reads off, for the current layer, a prune fraction per KV head. Those per-head keep counts get apportioned with a largest-remainder method familiar from apportioning parliamentary seats: floor each head's ideal count, then hand the leftover slots to whichever heads had the largest fractional remainder, so the total across all heads lands exactly on the intended sum instead of drifting from independent rounding.

Where does the curve come from? Per its abstract, LU-KV frames head-level budget allocation as "a global combinatorial optimization problem to maximize the long-horizon marginal contribution of reserved tokens": the curve is the output of an actual optimization run, not a shape someone picked by hand. That also means it isn't free the way a formula is. Generating a curve requires LU-KV's own companion repository: a step1 pass that extracts per-context scorer statistics by actually running the target model over a dataset, then a step2 pass that computes the averaged layer/head curve from those statistics. kvpress bundles exactly one ready-made curve, for Llama-3.1-8B-Instruct paired with ExpectedAttentionPress(epsilon=0.02), sink 4, window 1, fetched over HTTP from a raw GitHub URL the first time that exact model gets registered, then cached. Ask for any other (model, scorer) combination and LU-KV raises a KeyError rather than falling back to anything: there's no generic version of this that works on any model out of the box the way PyramidKV's formula does.

Simulated, not measured. The real curve is a [99, num_layers, num_kv_heads] array generated offline by actually running Llama-3.1-8B-Instruct over a dataset with Expected Attention, and it isn't something a browser can reproduce. This chart fakes an illustrative, irregular per-layer shape purely to make one point concretely: unlike PyramidKV's smooth, monotonic pyramid, a real data-driven curve doesn't have to be monotonic at all, it can bump up and down per layer in ways a hand-picked formula never would. The target_idx lookup itself, and the floor-based per-layer keep count, do mirror the real formula.

Where this shines, and where it doesn't

Because the curve is an actual optimization result rather than a hand-picked shape, it can in principle capture an irregular, non-monotonic allocation across layers and heads that reflects whatever a specific model actually does, something a single global beta shaping a smooth pyramid can never represent no matter how it's tuned. That's a strictly more expressive parameterization than PyramidKV's, at the cost of needing far more than a formula and a couple of scalar hyperparameters to produce it. The tradeoff shows up immediately outside the one bundled configuration: LU-KV isn't usable on a model or scorer combination nobody has already profiled, and that KeyError is the real price of the extra expressiveness. Generating a new curve means running an actual model over an actual dataset offline first, not tweaking a hyperparameter. It also inherits whatever the wrapped scorer gets wrong, same as PyramidKV, and the one bundled curve ties out-of-the-box behavior to one specific model, one specific scorer configuration, and one specific sink/window setting; step outside those and you're either building your own curve or you're not using LU-KV at all.

Real implementation

kvpress implements this as LUKVPress. See the source: lukv_press.py. Original paper: Tang, Jiao, Chen, Liu, Li, Chen, "Predicting Future Utility: Global Combinatorial Optimization for Task-Agnostic KV Cache Eviction," 2026, whose abstract states LU-KV "reduces KV cache size by 80% with minimal performance degradation."
