ChunkKV

TL;DR: Every scoring method in this catalogue ranks tokens one at a time and keeps the top-scorers, wherever they happen to land in the sequence. ChunkKV keeps that same per-token score but changes what gets evicted: it groups tokens into fixed-length chunks first, then keeps or drops a whole chunk at once, so survivors always show up in contiguous runs instead of scattered singletons.

Scattered survivors can strand what they need

Liu et al. point out that most eviction methods score and rank tokens in isolation, which can fragment a passage: if the two tokens that make a fact legible are three words apart and only one of them scores highly enough to survive, keeping just that one token doesn't actually preserve the fact. The KV cache itself is a real bottleneck: the paper cites it as consuming up to 70% of total memory during long-context inference. Their fix doesn't touch how importance gets measured; it changes the unit that eviction operates on, from a single token to a short run of neighboring ones.

Keep the score, change the unit

ChunkKV doesn't invent its own importance signal. In kvpress it wraps any other ScorerPress, the same score() logic that method would use on its own (SnapKV, Knorm, whichever press you hand it), computed exactly as that press would compute it. What ChunkKV changes is what happens after the scores exist: instead of ranking individual tokens and keeping a global top-k, it cuts the sequence into fixed-length chunks (chunk_length, 20 tokens by default), averages each chunk's token scores into a single chunk score, ranks the chunks, and keeps the top-scoring ones whole. Every token in a kept chunk survives; every token in a dropped chunk is evicted, regardless of how that individual token happened to score. A leftover partial chunk at the end, when the sequence length isn't a clean multiple of chunk_length, gets scored and ranked the same way, as one more chunk competing for a slot.

One real constraint: kvpress's implementation asserts the underlying press wasn't handed raw attention weights, so ChunkKV composes with scorers that compute importance from hidden states and keys directly, not with a press that needs eager attention output passed in.

Try it

Watch the chunk length slider: survivors always arrive in contiguous blocks matching that width, never as isolated tokens scattered across the sequence. kvpress's own default chunk length is 20, sized for much longer real sequences; this demo uses a smaller one so the blocking is visible on a 29-token sample.

Simulated, not measured. The per-token score behind this demo is a synthetic stand-in for whatever ScorerPress ChunkKV would actually be wrapping (SnapKV, Knorm, or anything else in this catalogue that produces one score per token). The chunk-averaging and ranking on top of it match kvpress's real ChunkKVPress.compress() logic exactly.

Where this shines, and where it doesn't

Because ChunkKV only changes the unit of eviction, not the scoring rule, it composes with anything else in this catalogue that produces a per-token score, rather than competing with it: point it at SnapKV and you get SnapKV's importance signal applied chunk-wise. The paper reports this pays off in practice: up to 8.7% better precision than comparable methods at the same compression ratio, across LongBench, Needle-in-a-Haystack, GSM8K, and JailbreakV. Its paper also describes a separate layer-wise index-reuse technique, good for a further 26.5% throughput gain by exploiting similarity across layers, worth flagging honestly: kvpress's ChunkKVPress implements the chunk-wise selection mechanism described above, not that throughput optimization. The tradeoff on the selection side is granularity: a single genuinely important token stranded inside an otherwise unremarkable chunk has no way to survive alone, and the chunk boundaries themselves are arbitrary fixed-length cuts, not real sentence or paragraph breaks, so a coherent unit can still straddle one. And because the importance signal itself comes entirely from whatever press ChunkKV wraps, it also inherits that press's weaknesses unchanged.

Real implementation

kvpress implements this as ChunkKVPress, a wrapper around a ScorerPress whose compress() reshapes that press's global scores into chunks of chunk_length, averages within each chunk, and keeps the top max(1, int(n_chunks * (1 - compression_ratio))) chunks via gather. See the source: chunkkv_press.py. Original paper: Liu, Tang, Dong, Li, Liu, Li, Hu, Chu, "ChunkKV: Semantic-Preserving KV Cache Compression for Efficient Long-Context LLM Inference," 2025.
