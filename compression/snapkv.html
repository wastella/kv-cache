SnapKV

StreamingLLM and H2O both operate during generation, evicting as new tokens arrive. SnapKV does its compression once, at the end of prefill — before a single token has been generated — by using the end of the prompt itself as a preview of what the model is about to ask for.

The prompt already tells you what it needs

Li et al. observed that the attention pattern of the last few tokens of a prompt — the observation window — is a strong predictor of what the model will keep attending to during generation. Intuitively: the tail end of a prompt (often an instruction, like "… summarize the above" or "… answer the question below") is where the model's actual intent lives, and its attention already points at the parts of the context that matter for that intent.

So instead of waiting to observe attention during generation like H2O, SnapKV computes, once, how much attention each token in the observation window pays to every earlier token, pools those scores together, and keeps the top-scoring tokens (plus the window itself). The rest of the cache is compressed before generation even begins — which means the memory savings start immediately, not gradually.

Where this shines, and where it doesn't

Because it works entirely from the prompt, SnapKV is a strong fit for long-document workloads with a short, focused instruction at the end — RAG, document QA, summarization of a known task. It compresses once and is done, with no ongoing scoring overhead during decode. The assumption it leans on is also its main limitation: if the instruction is vague, appears before the relevant context rather than after it, or the model's real information need only becomes clear partway through generation, the observation window is a weaker predictor and the compression can discard tokens that turn out to matter.

Real implementation

kvpress's SnapKVPress.score() takes attention from the last window_size prompt tokens (64, by default) to every earlier one, averages it across those queries, then runs it through a small average-pooling kernel before ranking. That pooling step is what keeps neighboring important tokens together instead of scattering the surviving set across isolated positions — the SnapKV paper found that keeping only scattered top-scorers, without pooling, tends to chop up the context and drop tokens a later one still needed. The window itself is padded to the max score so the ranking can never prune it. See the source: snapkv_press.py. Original paper: Li et al., "SnapKV: LLM Knows What You are Looking for Before Generation," 2024.
