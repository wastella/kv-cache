Expected Attention

TL;DR: SnapKV predicts what generation will need by observing real attention from the last few prompt tokens. Expected Attention doesn't observe anything from generation, real or simulated: it estimates the mean and spread of the queries the model has already issued, rotates that estimate forward to represent likely future query directions, and computes, in closed form, how much attention a key can expect to receive from a query drawn from that estimate.

What the score actually is

This method is kvpress's own contribution rather than an implementation of an outside paper, so the docstring in expected_attention_press.py is the primary source, and it lays out five steps directly:

  1. Compute the mean and covariance matrix of the queries before RoPE.
  2. Compute the RoPE rotation matrix on the next n_future_positions and average it.
  3. Apply that averaged rotation to the mean and covariance of the queries.
  4. Since attention is A = exp(Q @ K / sqrt(d)), compute the expected attention E(A) = exp(K @ mean.T / sqrt(d) + 1/2 K @ cov @ K.T / d).
  5. Rescale the resulting scores by (scores + epsilon) * ‖V‖₂.

Step 4's formula is the theoretical target; what score() actually computes is a softmax over mean_query · key / sqrt(d) plus a quadratic covariance correction term, divided by d, then run through softmax across all cached keys. That's not literally the same as normalizing the raw exp(...) expression in step 4, since real attention itself is a softmax over per-key scores, not an unnormalized exponential, so the softmax is doing the normalization the docstring's formula leaves implicit.

Mean, covariance, and a forward-rotated RoPE

The mean and covariance are both computed from the model's own past queries, before rotary position embeddings are applied, dropping the first n_sink hidden states first (avoiding outlier statistics from sink tokens). Query direction alone (the mean) is a first-order estimate of what future queries will look like; use_covariance (on by default) adds a quadratic correction term capturing how much queries actually vary around that mean, not just where they center. Because RoPE rotates queries by however many positions have passed, and future queries will sit at positions that don't exist yet, the method builds an averaged rotation matrix over the next n_future_positions (512 by default) and applies that single averaged rotation to both the mean and the covariance, rather than trying to guess an exact future position.

As with CriticalKV, the resulting score is optionally rescaled by the L2 norm of each token's value vector (use_vnorm, on by default): a key that scores well but whose value barely moves the output gets pulled back down. That's exactly the overlap CriticalKV's source code warns about: wrapping an ExpectedAttentionPress with use_vnorm still enabled double-counts a value-magnitude rescale that both methods apply. The first n_sink keys (4 by default) are excluded from scoring entirely and padded back in above the maximum score afterward, so they rank first in line for whatever budget remains, the same sink-token treatment used elsewhere on this site.

The Stats variant: skip the live prompt entirely

Computing mean and covariance from the current prompt's own hidden states works, but a short prompt gives a noisy estimate of a head's "typical" query behavior. ExpectedAttentionStatsPress sidesteps that by loading precomputed query statistics instead: its post_init_from_model() either reads them from a local stats_folder or fetches them from a Hugging Face Hub collection keyed by the model name, the calibration dataset, and how many samples were used. The default calibration setup collects statistics from 100 samples of kmfoda/booksum at a sequence length of 1000 tokens, computed once per model, offline, and reused across every request that model serves afterward, via expected_attention_with_stats.py's own collect_queries() function. If no matching statistics exist for a given model on the Hub, the press fails loudly rather than falling back silently: it raises an error telling you to run that collection script yourself first.

Where this shines, and where it doesn't

Unlike SnapKV, this method doesn't lean on there being a specific "instruction at the end of the prompt" to observe: it's modeling the query distribution statistically rather than reading one concrete slice of it, so it doesn't degrade the same way when a prompt has no clean observation window. And unlike Knorm, it's actually forecasting attention toward a rotated future direction, not relying on a static per-key property alone. The Stats variant goes further and removes the live-prompt dependency altogether. The cost is real complexity: this needs access to the model's RoPE machinery (rotary_emb, per-head cos/sin) to build the averaged rotation, and, with covariance enabled, a real head_dim x head_dim covariance computation per head, meaningfully heavier than a norm-only method like Knorm or a straightforward attention average like SnapKV. The Stats variant adds its own dependency too: it's only as good as the offline calibration set (currently a fixed catalog of pre-uploaded statistics on the Hub), and using it on a model that isn't already covered means running the collection step yourself before you can use it.

Real implementation

kvpress implements this as ExpectedAttentionPress and ExpectedAttentionStatsPress. No separate paper backs this one; the docstrings and source are the primary reference. See the source: expected_attention_press.py and expected_attention_with_stats.py.
