compression / dimension-pruning

ThinK

Every method up to this point compresses the cache by deciding which tokens to keep. ThinK doesn't touch that axis at all — it shrinks each kept key vector itself, by pruning the individual dimensions (channels) that turn out to carry the least signal.

Redundancy in a different axis

Xu et al. looked at the channel dimension of the key cache — not the sequence-length axis every eviction method in this catalogue operates on — and found real redundancy there too: a key vector's dimensions contribute very unevenly to attention. The per-channel magnitude distribution is uneven, and the attention weights that result show a low-rank structure. Some dimensions are doing real work; plenty are close to dead weight, consistently, across many cached tokens.

ThinK scores each channel by multiplying two magnitudes: how hard the last window_size queries lean on that channel (mean squared query value, averaged over that window), and how hard every key currently sitting in the cache leans on it (mean squared key value, averaged over the entire cache, not just the window). That score is a property of the head as a whole, not of any one token, so the pruning decision is "which channels are useless for this attention head," not "which channels are useless for this specific token" — every kept token in that head loses the same slice of its vector.

Simulated, not measured. The per-channel importance scores here are generated locally from a deterministic seed, not computed from real query/key magnitudes — illustrative of which channels get pruned and shared across tokens, not extracted from a real model.

Where this shines, and where it doesn't

Because ThinK prunes channels rather than tokens, it's compressing an orthogonal axis to everything else in this catalogue — it composes with any token-eviction method instead of competing with it for the same budget (kvpress's own docs give ComposedPress([SnapKVPress(0.5), ThinKPress(0.5)]) as an example, stacking both savings). The cost is that the pruning decision is coarser than a per-token method: it's the same channel mask for every token in a head, so a channel that's dead weight on average but briefly important for one specific token has no way to survive. There's also a practical wrinkle: kvpress's current implementation zeroes pruned dimensions rather than physically shrinking the stored tensor, so realizing the memory savings in deployment needs an extra packing step beyond what's in the library today.

Real implementation

kvpress implements this as ThinKPress, which re-derives windowed query states, scores key channels by queries_norm * keys_norm, and scatters zeros into the lowest-scoring dimensions. See the source: think_press.py. Original paper: Xu, Jie, Dong, Wang, Lu, Zhou, Saha, Xiong, Sahoo, "ThinK: Thinner Key Cache by Query-Driven Pruning," 2024.
