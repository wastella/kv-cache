compression / reconstruction-based

KVzip

TL;DR: Every other method in this catalogue scores a cached KV pair by watching attention happen, either live during decoding or in a prompt-reading pass beforehand. KVzip does something stranger: it hands the model back its own context and asks it to repeat it, then measures which cached KV pairs that reconstruction actually leaned on. What survives is whatever turned out to be necessary to rebuild the context, not whatever a query happened to attend to.

Scoring by asking the model to prove it needed something

KVzip's importance signal has nothing to do with any real user query. After the prompt is prefilled once, KVzip re-feeds chunks of that same context back into the model as a repeat-the-context instruction, reusing the KV cache that's already sitting there. As the model generates the repeated text, its queries attend back over the original cached keys, and KVzip records, for every cached position, the maximum cross-attention weight it ever received during that reconstruction across the chunks it appears in. A KV pair that reconstruction never needed to lean on gets evicted; one it repeatedly attended to survives. It's an importance measurement derived entirely from whether the context is reconstructible without a given entry, not from any downstream task at all, which is what makes it query-agnostic: the same compressed cache can serve any question about the context, because nothing about the scoring depended on what the question was going to be.

The first n_sink positions (4 by default) are exempted from this and simply forced to the maximum score, the same attention-sink logic StreamingLLM uses, on top of the reconstruction signal everywhere else.

The cost, and where the granularity actually lives

This isn't free. kvpress's own implementation logs a warning that the chunked reconstruction pass adds "a computational overhead of 2–3 times the initial prefilling cost," on top of the prefill that already happened, because the model effectively has to read most of its own context a second time before any tokens can be evicted.

The eviction decision itself is also finer-grained than a single kept/evicted call per token. Scores are tracked per layer and per KV head, and by default kvpress lets the pruning budget float freely across layers rather than forcing a uniform ratio everywhere (a layerwise=True flag switches to a fixed per-layer ratio instead). That means two attention heads in the same layer can end up keeping different token positions, something the simple keep/evict grid below can't show directly, it's drawn for one representative layer and head, the same simplification ThinK's per-channel grid makes elsewhere in this catalogue.

Where this shines, and where it doesn't

Because the score comes from reconstruction rather than any live query, the same compressed cache is meant to generalize across whatever gets asked about the context afterward, instead of being tuned to one observation window the way SnapKV is. The paper reports 3-4x cache size reduction with roughly 2x faster decoding, evaluated on LLaMA3.1, Qwen2.5, and Gemma3 with contexts up to 170K tokens, and claims to outperform other query-agnostic eviction methods it was compared against. The tradeoff is the reconstruction pass itself: 2-3x prefill overhead is a real cost paid up front for every request, before any memory is actually saved, which makes KVzip a worse fit for latency- sensitive short contexts than for long documents amortizing that cost over a much bigger cache. kvpress's own docstring also flags that this implementation prioritizes fidelity to the algorithm over runtime efficiency, and points to the original repository for a version without that overhead (at a stated cost to compression quality). It's also explicitly unsupported for Gemma3 models in kvpress specifically, despite Gemma3 being one of the architectures the original paper evaluates.

Real implementation

kvpress implements this as KVzipPress. See the source: kvzip_press.py. The docstring is explicit that this is a minimal-changes port, not the fully optimized version: for that, including a variant without runtime compression overhead, see the original repository, snu-mllab/KVzip. Original paper: Kim, Kim, Kwon, Lee, Yun, Song, "KVzip: Query-Agnostic KV Cache Compression with Context Reconstruction," NeurIPS 2025 (oral).

See also RestoreKV, which builds a learned restoration mechanism on top of this exact scoring pipeline.
