RestoreKV

TL;DR: KVzip decides what to evict by reconstruction. RestoreKV keeps that exact evictor, but spends a small slice of the same cache budget on something new: a handful of learned "restore" cache entries, produced by a one-time LoRA-adapted pass over the full context, trained to approximate what a full, uncompressed cache would have known. It's not a scoring rule at all, it's a trained recovery mechanism sitting alongside one.

Budget-matched, not budget-additive

Before eviction happens, RestoreKV runs one extra forward pass: a fixed number of learned "restore tokens" (8 per kvpress's adapters) attend over the entire, still-uncompressed KV cache in a single pass with a LoRA adapter enabled, and the K/V those restore tokens produce gets appended to the cache. That LoRA adapter is active for this one pass only; the base model's own forward passes never see it. Only the restore token embeddings and the LoRA weights are trained, roughly 0.4% of the model's parameters, and they're trained by self-distillation: the restore-augmented, compressed model is pushed to match what a full, uncompressed cache would have produced for the same context.

Critically, this doesn't add to the cache budget, it's carved out of it. kvpress's compress_post temporarily inflates the compression ratio it hands to KVzip's evictor by exactly num_restore_tokens / context_length, evicts more of the original context to compensate, then appends the n restore entries back in. The arithmetic works out so the total number of cache slots after both steps, real context tokens plus restore entries, matches what plain KVzip would have used at the requested ratio. RestoreKV isn't spending extra memory on restoration; it's trading some of the context tokens KVzip would have kept for a few tokens trained to approximate what got lost.

Where this shines, and where it doesn't

On Qwen3-4B, the paper reports improvements in 59 of 60 paired, budget-matched settings against baselines evicting at the same total cache size, and cites one baseline going from 38.2 to 73.2 accuracy at a 5% budget on a standard benchmark once RestoreKV's restoration is added on top of it. The core idea, being budget- matched rather than budget-additive, means the comparison to a plain evictor is fair: RestoreKV isn't winning by secretly using more memory. The cost is that this is no longer a training-free, drop-in method the way most of this catalogue is: it requires a model-specific adapter trained in advance, kvpress currently ships adapters (via Hugging Face, loaded automatically from the model name) for exactly two base models, Llama-3.1-8B-Instruct and Qwen3-8B, so it doesn't generalize to an arbitrary checkpoint the way Knorm or KeyDiff do. It also inherits every cost KVzip already pays (the 2-3x reconstruction-pass overhead) and adds one more forward pass, the restore-token encoding, on top.

Real implementation

kvpress implements this as RestoreKVPress, a subclass of KVzipPress that overrides compress_post to run the restore pass and inflate the ratio before delegating back to KVzip's own eviction logic. See the source: restorekv_press.py. Original paper: Baek, Shin, Kong, "RestoreKV: Recovering Full-Cache Behavior Under Aggressive Query-Agnostic KV Cache Eviction," 2026.
