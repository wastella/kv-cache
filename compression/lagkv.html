LagKV

TL;DR: Every attention-based method in this catalogue needs an actual attention weight from somewhere, a window, a decode step, an accumulated total. LagKV needs none of that: it never looks at attention at all. It slices the cache into fixed-size partitions and scores each one purely by comparing it to the partition that comes right after it.

Comparing the cache to itself

Liang, Zhang, Li, and Li's premise is that a token's key and value vectors already carry enough signal to judge importance, without ever consulting how a query actually attended to them. That makes LagKV attention-free in a stronger sense than a method like Knorm: Knorm still needs a single scalar (a key's norm) computed once from that key alone. LagKV goes further and scores each token relative to a whole different group of other tokens, the partition right after it in sequence order, what the paper calls "lag-relative information."

The mechanics: the first n_sink tokens (4 by default) get a fixed top score, sink-style. The rest of the sequence, minus a trailing "recent" region that gets the same fixed top score, gets sliced into fixed-size partitions of lag_size tokens (128 by default). For every partition except the last, LagKV looks one partition ahead: it takes the per-channel min and max that the next partition establishes for the key and value vectors, rescales every token in the current partition against that range, and measures how inconsistently each token's rescaled value spreads across channels. A token that lands consistently within the next partition's typical range looks unremarkable; one whose rescaled profile swings widely across channels stands out, and gets ranked higher within its own partition. Key-side and value-side versions of this score are averaged together.

Each partition (outlined box) is scored against the next partition to its right, never against itself. The sink and the trailing window score above every middle-partition token, so they're the first to fill the budget; push the ratio hard enough and even they start getting cut.

Where this shines, and where it doesn't

Not touching attention at all is a real practical advantage: LagKV doesn't need eager attention output, a held-out observation window, or any per-step bookkeeping, which the paper argues makes it easier to drop into existing serving stacks than attention-based alternatives. On RULER, the paper reports it outperforming SnapKV and StreamingLLM across compression ratios, and on 64-digit passkey retrieval, over 50% better than the attention-based H2O method at matched compression. The tradeoff is exactly what you'd guess from an attention-free method: comparing a partition to its neighbor is a proxy for "this token is unusual relative to what comes next," not a measurement of whether the model actually attended to it, so it can miss tokens that are important for reasons the key/value geometry alone doesn't surface. There's also a real floor on how short a sequence LagKV can act on at all: the code requires at least n_sink + 2 * lag_size tokens before it does any partition-relative scoring; shorter than that, it doesn't compress, regardless of the requested ratio. With the real defaults (n_sink=4, lag_size=128), that's roughly 260 tokens of headroom before LagKV does anything.

Real implementation

kvpress implements this as LagKVPress. Its score() reshapes the cache into partitions of lag_size, calls _get_states_score() to rescale each partition against the next one and take a per-channel standard deviation, then (by default, cross_scoring=False) replaces that with each token's rank within its own partition, normalized to [0, 1). Sink and trailing-window tokens get a score of exactly 1. See the source: lagkv_press.py. Original paper: Liang, Zhang, X. Li, J. Li, "LagKV: Lag-Relative Information of the KV Cache Tells Which Tokens Are Important," 2025.
