TOVA — Token Omission Via Attention

H2O keeps a running, accumulated attention score per token across every generation step. TOVA throws that history away: at each decoding step it looks only at the attention the current token just paid, decides what to keep from that one snapshot, and repeats the whole decision from scratch next step.

A transformer as a bounded RNN

Oren et al. frame the comparison directly: a decoder-only transformer can be viewed as a recurrent network with an unbounded hidden state — the KV cache is that state, growing by one entry per token instead of being folded into a fixed-size vector the way a real RNN's hidden state is. Capping the KV cache size is, in this framing, exactly what it takes to turn a transformer into a genuine bounded multi-state RNN. TOVA is the eviction policy they propose for doing that: at each decoding step, take the current token's attention distribution over every token still in the cache (averaged across heads), and if the cache is over budget, drop whichever token gets the least attention from that single query.

The structural difference from H2O is that TOVA keeps no running statistics at all. A token that was a heavy hitter for the last fifty steps but gets ignored on this one step is a candidate for eviction right now — nothing about its history protects it. That's much simpler state to maintain (one attention row instead of an accumulator per token) but a noisier signal, since one query's attention pattern can swing sharply from the next query's.

Try it

Darker tokens received more simulated attention from the current decoding step alone. Move the decode-step slider and watch which tokens are kept reshuffle — that volatility is what TOVA trades away by not keeping H2O's accumulated score.

Simulated, not measured. As with the H2O and SnapKV demos, "attention from the current step" here is a locally generated stand-in (a recency term plus a few random spikes reseeded per decode step) — illustrative of the mechanism, not extracted from a real model.

Where this shines, and where it doesn't

Minimal bookkeeping is the whole appeal: one attention row per step, no per-token running total to carry over from the last one. The paper's framing also makes the cache-size/quality tradeoff unusually explicit — you're literally choosing the hidden-state size of a bounded RNN. The cost is exactly the volatility that simplicity buys: eviction decisions can flip from one step to the next, so a token that's genuinely important but only momentarily under-attended — because the current query happens to be about something else — can be evicted before its importance shows up again.

Real implementation

kvpress implements this as TOVAPress: it takes the last query's attention weights, averages them across heads to get one score per cached position, then overwrites the score of the token just added with the row's max score (plus a hair more) so it can't be the one evicted this step. See the source: tova_press.py. Original paper: Oren, Hassid, Yarden, Adi, Schwartz, "Transformers are Multi-State RNNs," 2024.
