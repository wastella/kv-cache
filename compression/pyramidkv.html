PyramidKV

Every method so far answers "which tokens matter?" and applies that same answer to every layer of the model. PyramidKV asks a different question: how much cache budget does each layer even need? — and gives early layers more room than late ones.

Information funnels as it goes up

Cai et al. traced how attention actually spreads across layers in a decoder-only transformer and found a consistent shape to it: in early layers, attention is broad — a token ends up attending fairly evenly across much of the context. By the later layers, attention narrows sharply, concentrating on a small set of tokens the model has already decided matter (often the same handful across many later layers). They call this pyramidal information funneling — wide at the base, narrow at the top.

If later layers only meaningfully attend to a handful of tokens anyway, giving them the same cache budget as early layers is wasted space. PyramidKV allocates a shrinking budget per layer — derived from a target compression ratio, a small fixed window for the most recent tokens, and a beta parameter controlling how steep the pyramid is — instead of one flat ratio everywhere. It reuses SnapKV's observation-window scoring to decide which tokens fill each layer's budget; what it changes is how many slots each layer gets, based purely on depth.

Try it

This isn't a token grid like the other pages — PyramidKV doesn't change which tokens are picked, it changes how large each layer's budget is. The chart below reproduces kvpress's actual get_layer_budget() formula against our 29-token sample sentence, across 12 simulated transformer layers.

Each bar is one layer's kept-token budget out of 29. Push beta toward 1 and the pyramid flattens out — every layer gets the same budget, the gentlest possible shape. Raise it and the gap between the earliest and latest layer widens.

Where this shines, and where it doesn't

Because the axis being compressed here (how much budget each layer gets) is orthogonal to the axis every other method in this catalogue compresses (which tokens survive), PyramidKV composes naturally with per-token scoring — which is exactly how kvpress implements it, as a subclass of SnapKVPress that overrides only the budget calculation. The gain is real: by construction, the total budget summed across every layer works out to roughly what flat SnapKV would use at the same compression ratio — PyramidKV isn't shrinking the cache any further, it's redistributing that same total so layers that don't need the room lose it and layers that do keep it, buying back accuracy a flat split leaves on the table. The tradeoff is that the pyramid shape is a global hyperparameter tuned somewhat empirically rather than derived per-model, so a poor beta or window size for a given architecture can under- or over-allocate layers relative to what they actually need — and near the extremes of the compression-ratio range (very light compression or very aggressive) the shape constraints can't be satisfied at all, in which case it silently falls back to a flat, SnapKV-style budget. PyramidKV also still inherits whatever weaknesses its underlying token-scoring method has, since it isn't changing which tokens are chosen, only how many.

Real implementation

kvpress implements this as PyramidKVPress, a subclass of SnapKVPress whose get_layer_budget() computes a shrinking per-layer capacity from compression_ratio, window_size, and beta. See the source: pyramidkv_press.py. Original paper: Cai, Zhang, Gao, Liu, Li, Liu, Lu, Xiong, Dong, Hu, Xiao, "PyramidKV: Dynamic KV Cache Compression based on Pyramidal Information Funneling," 2024.
