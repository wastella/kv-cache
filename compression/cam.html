CaM: Cache Merging

TL;DR: Every eviction-based method in this catalogue makes the same choice for a low-scoring token: drop it, its key and value are gone. CaM makes a different choice for some of them. Before a token is pruned, it's given a chance to fold its value vector into the kept tokens right after it, so some of what it knew survives even though its own slot in the cache doesn't.

A coin flip for every evicted token

CaM sits on top of an ordinary scorer, kvpress calls it the base_press, which ranks cached tokens exactly the way a method like H2O or TOVA would. The lowest-scoring tokens are still marked for eviction. What changes is what happens to them next, for each evicted token, a target window of the next several kept tokens immediately following it, in sequence order, is identified (merge_budget tokens, 32 by default).

Whether that evicted token actually merges into its window is decided by a Bernoulli coin flip, weighted by how much cumulative attention the evicted token earned relative to the average cumulative attention of the tokens in its window: clamp(A_evicted / mean(A_window), 0, 1). A token that was pulling noticeably more attention than its neighbors has a good chance of merging in; a token that was already close to irrelevant mostly doesn't. When the coin comes up in favor of merging, the evicted token's value vector, not its key, is divided by the window size and added into every kept token's value in that window. When it doesn't, the token is simply evicted, no different from any other method in this catalogue.

Only values get merged; an evicted token's key is discarded either way. That's a real asymmetry in the algorithm: what survives a merge is a smoothed trace of the evicted token's contribution blended into its neighbors' outputs, not anything a future query could specifically attend back to.

Try it

Solid tokens are kept outright. Dashed, struck-through tokens with an arrow merged their value into up to 3 kept tokens just after them (illustrative, real kvpress defaults to 32). Plain struck-through tokens lost their merge coin flip and were evicted with nothing carried forward. Tokens outlined in the accent color received at least one merge contribution.

Simulated, not measured, and simplified. The importance scores, cumulative-attention values, and Bernoulli draws here are all synthetic, seeded from each token's text rather than measured from a real base press and real attention accumulation. This demo also simplifies which evicted tokens are even eligible to merge: kvpress's real batched implementation only considers the tokens added since the last compression pass as merge candidates (governed by internal step-counting bookkeeping this demo doesn't model); here, every evicted token gets a shot at merging, so the mechanism stays visible. The merge-or-not rule itself, the probability formula and the value-averaging into the window, is the real one from CAMPress.compress.

Where this shines, and where it doesn't

The point of merging instead of dropping is to reduce the output perturbation eviction causes: a token that was contributing a little to a lot of future outputs doesn't just vanish, some residue of it keeps propagating through the tokens it merged into. The paper's own experiments, run across LLaMA, OPT, and GPT-NeoX, report this improves memory-efficient LLM inference relative to eviction alone, though the abstract itself doesn't commit to a specific headline number, so treat "how much better" as benchmark-dependent rather than a single figure. The cost is complexity on every axis: a Bernoulli draw and a value-averaging step for every evicted token instead of a single sort, a merge_budget window size to tune, and, notably, this kvpress implementation doesn't use a single global compression ratio the way most of this catalogue does. It targets an absolute target_size (2048 tokens by default) and only triggers a compression pass every compression_interval decode steps (512 by default), batching many steps' worth of eviction into occasional bulk passes rather than compressing continuously. That's a real difference in how you'd configure it, not just an implementation detail.

Real implementation

kvpress implements this as CAMPress, which wraps a configurable base_press scorer and overrides compress() to merge before pruning. See the source: cam_press.py. Original paper: Zhang, Du, Luo, Zhong, Zhang, Liu, Ji, "CaM: Cache Merging for Memory-efficient LLMs Inference," ICML 2024.
