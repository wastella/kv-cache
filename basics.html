01 — basics

What is a KV cache?

Short version: it's memoization for attention. Without it, generating the Nth token would mean recomputing attention over all N-1 previous tokens from scratch, every single step. The KV cache stores the result of that work so it only has to happen once per token.

Where keys and values come from

Inside every attention layer, each token is projected into three vectors: a query, a key, and a value. Attention works out how much each token should "listen" to every other token by comparing queries against keys, then uses those weights to blend the values.

The key insight for generation: once a token has been processed, its key and value vectors never change again. Its query vector was only ever needed to figure out its own output — but its key and value stick around as something every future token will need to compare against. So instead of recomputing them, the model caches them.

Two phases

Prefill: the entire prompt is processed at once, in parallel, and a key/value pair is computed and cached for every token in it. This is the expensive-but-parallel step.

Decode: the model generates one new token at a time. Each step only computes a query, key, and value for the single new token, appends the new key/value to the cache, and attends over everything cached so far. This is the cheap-per-step-but-sequential part.

A toy sequence: the first few steps are prefill (the whole prompt lands in the cache at once), the rest is decode (one token appended per step).

Why the cache becomes a problem

Cache size scales with layers × heads × head_dim × 2 × sequence_length (the 2 is for storing both keys and values), multiplied again by batch size. Every one of those factors is fixed by the model and your workload except sequence length — which keeps growing for as long as you keep generating or feeding in context.

Concretely: serving Llama 3.1-70B at a 1M-token context in fp16 can require on the order of 330GB just for the KV cache — more than the model's own weights. That memory has to sit in GPU memory for the entire lifetime of the request, and it's per request, so it also caps how many requests you can serve at once.

This is the problem KV cache compression solves. Instead of keeping every token's key and value forever, compression methods decide which ones can be dropped, merged, or stored more cheaply — with as little damage to output quality as possible.
