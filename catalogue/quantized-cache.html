Quantized KV cache

Every method so far shrinks the cache by throwing something away — tokens, or channels within a token. Quantization keeps everything and shrinks it a different way: store each surviving number in fewer bits.

The cache doesn't need full precision

Liu et al.'s KIVI studied the actual distribution of values inside a running KV cache and found consistent structure worth exploiting: within the key cache, outlier magnitudes cluster by channel (so keys quantize better when grouped and scaled per channel), while within the value cache outliers cluster by token instead (so values quantize better grouped per token). Respecting that asymmetry — rather than quantizing the whole cache with one flat scheme — is what let KIVI push all the way to 2-bit KV caches while staying close to full-precision quality on models that degrade badly under naive, uniform quantization.

kvpress doesn't implement any of this itself — it delegates entirely to Hugging Face transformers' QuantizedCache (via the quanto or hqq backend), so quantization is a cache object you hand to the pipeline (QuantizedCache(backend="quanto", nbits=4)) rather than a press with a score() method. That's a meaningfully different shape from everything else in this catalogue: it's cache infrastructure, applied independently of whichever token- or channel-pruning press is also running. transformers' implementation is inspired by KIVI but doesn't replicate its asymmetric axes — by default it quantizes both keys and values per-channel in fixed-size groups, which its own source comments describe as "in contrast to what was described in the [KIVI] paper." It does keep one piece of the paper's spirit: the most recent residual_length tokens (128 by default) stay in full precision, so quantization error never touches the tokens closest to the current decoding step.

Where this shines, and where it doesn't

Because quantization operates on numeric precision rather than on which tokens or channels survive, it stacks directly with every other method in this catalogue — run SnapKV or H2O to decide what stays, then quantize whatever's left, and the two savings multiply instead of trading off against each other. It's also comparatively gentle as compression goes: dropping a token can lose a specific piece of information outright, while a lightly quantized value is still an approximation of the original, just noisier. The costs show up in throughput and precision edge cases rather than architecture — dequantizing before every attention computation adds latency, aggressive bit-widths (2-bit and below) start to measurably hurt quality on some models and tasks the way any lossy compression eventually does, and using it means one more dependency (optimum-quanto) to install and keep working.
