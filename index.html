Understanding the KV cache, and how to shrink it.

Every transformer that generates text one token at a time keeps a growing cache of key and value vectors so it never has to recompute attention over the whole prompt again. That cache is simple in concept and expensive in practice — long contexts can push it past the size of the model itself. This site walks through what it is and how researchers compress it, with small interactive demos instead of just equations.

Compression

Eight compression methods, ported from NVIDIA's kvpress, spanning position, attention, prediction, norm, layer-wise, channel, and quantization-based approaches. Every demo lets you adjust the compression ratio and watch which tokens (or channels, or bits) survive.

  • StreamingLLM position-based
    Keep a handful of "sink" tokens plus a sliding recent window. No scoring required.
  • H2O — Heavy-Hitter Oracle attention-based
    Track cumulative attention per token; a small set of "heavy hitters" earns most of it.
  • SnapKV prediction-based
    Use attention from the end of the prompt to predict which earlier tokens will matter, before generation even starts.
  • Knorm norm-based
    Score cached keys by nothing but their own L2 norm — no attention weights needed, the cheapest method here.
  • PyramidKV layer-wise
    Give early layers a bigger cache budget than late ones, instead of one flat ratio for every layer.
  • TOVA — Token Omission Via Attention attention-based
    Score tokens from only the current decoding step's attention, recomputed fresh every step.
  • ThinK dimension-pruning
    Prune the least useful channels inside each kept key vector, instead of dropping whole tokens.
  • Quantized KV cache quantization
    Keep every token, but store each one in fewer bits. Stacks with any eviction method above.
More methods are coming. kvpress implements 40+ presses; this catalogue currently covers 8 of them, spanning most major families. See about for how these were chosen.
